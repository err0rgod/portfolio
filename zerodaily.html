§3Four repositories

Each subsystem is its own repo, its own CI, its own deploy gate

$ gh repo view err0rgod/bot1 --json name,description

err0rgod/bot1 ↗
The ingestion engine. Containerized Python 3.12 Lambda on an 8-minute cron: RSS scrape → LLM semantic dedup → two-tier extraction (cloudscraper, Firecrawl fallback) → SSRF-guarded media pipeline → dual-persona Bedrock roasting → DynamoDB.
the serving layer · live at api.zerodaily.in ↗
FastAPI behind Mangum on a Lambda Function URL, DynamoDB single-table + GSIs, edge-cached through Cloudflare - plus a Streams worker that fires FCM push and pre-warms the CDN when breaking news lands. (private repo)
the phone app · get the apk ↗
React Native / Expo SDK 52, Inshorts-style vertical swipe, 0ms cold boot from disk cache, N−8 prefetch, on-device personalization (18% exploration, anti-clumping), FCM topic push with zero server-side device tokens. (private repo)
err0rgod/zerodaily-web ↗
The front door. Vite + Tailwind static site on Cloudflare Pages (~4.5KB gzipped CSS), live breaking-news wire, and a /apk gateway that 302s to the latest GitHub Release - so the site never redeploys for a new app version.

§4Details

The details that don't show up in a demo

$ dig +short api.zerodaily.in

  • CDN pre-warming on breaking news - when a breaking article hits DynamoDB, the Streams worker purges the affected feed URLs via Cloudflare's API, then issues HTTP GETs against the feeds + up to 20 fresh image URLs. The first real user gets a cache hit, not a cold Lambda.
  • Atomic notification cooldown without Redis - a DynamoDB conditional write (attribute_not_exists OR ttl <= now) per category gives a 30-minute anti-spam lock that fails closed: any unexpected DB error suppresses the notification instead of risking a storm.
  • SSRF defense that actually resolves DNS - the media pipeline resolves hostnames pre-connection and rejects RFC-1918, loopback, link-local, and 169.254.169.254 (AWS metadata), strips user:pass@host, blocks file:///gopher://, then streams with a 10MB ceiling in 64KB chunks.
  • Prompt-injection sandboxing - scraped article text is wrapped in <untrusted_article_content> boundaries; the system prompt instructs the LLM to treat it strictly as data; control characters and null bytes are purged; outputs are schema-bounded.
  • Dual-provider LLM resilience - AWS Bedrock primary, direct API failover with exponential backoff + jitter, and in-memory circuit breakers so a sick provider stops getting called.
  • Semantic dedup before scraping - the LLM clusters 15 candidate headlines down to ~4 unique stories before any HTTP fetch, cutting downstream bandwidth and inference spend by ~75%.
  • Two-stage deploys with smoke-test gates - bot1 deploys to a test Lambda, invokes it with a real payload, greps for errors, and only then promotes to prod. The backend workflow curls live /health and feed endpoints and aborts on non-200.
  • Image pipeline with a guilty conscience - Pillow LANCZOS to 800px WebP (q=80, method=6 → 70–85% smaller), a 25M-pixel decompression-bomb guard, and a DB interceptor that strips any non-CDN image URL at write time. No hotlinks reach production.
  • On-device personalization - the app's ranking (18% exploration, max 1 consecutive same-category card, 24h time-decay half-life) runs locally; reading history is an O(1) in-memory Set in front of AsyncStorage so swipes never block on disk.
  • Zero device tokens - FCM topic-based messaging means the server never stores a single device token. Clients self-subscribe to topic_{category} and topic_breaking_all.

§5From the code

The atomic cooldown lock, verbatim from the stream worker

$ aws dynamodb list-tables --region us-east-1

# 30-min anti-spam lock per category - no Redis, fails closed
table.put_item(
    Item={
        "id": f"NOTIF_COOLDOWN#{category}",
        "ttl": now + 1800,
    },
    ConditionExpression="attribute_not_exists(id) OR #ttl <= :now",
)
# ConditionalCheckFailedException ⇒ another instance already fired.
# Any unexpected error ⇒ suppress the notification. Never storm.
